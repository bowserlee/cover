# Cover — Design Spec

**Date:** 2026-05-17
**Status:** Draft, pending user review
**Project:** Cover — group bill splitting PWA
**Author:** Bauer Lee (with Claude as co-founder)

---

## What this is

Cover is a Progressive Web App for group bill splitting at restaurants and shared expenses. Snap a receipt, assign items to people, and each person gets a personalized Venmo link delivered through their phone's native share sheet. Reminders for unpaid balances fire from the host's phone in a single tap.

The product is **intentionally not novel**. Splitwise, Plates, Venmo, Cash App, Tricount, and a dozen others occupy this space. This is a deliberate exercise in rebuilding a proven category to demonstrate the asymmetry between 2011 startup-team effort and 2026 single-builder-with-AI-tools effort.

## Class thesis

> *Splitwise was built by a small team in 2011 and took years to reach product-market fit. In 2026, one freshman rebuilt the core product in 10 weeks, with zero ongoing API costs and zero team. The asymmetry between yesterday's team output and today's individual output is the entire point.*

**The product is the artifact. The build process is the demo.**

## Goals (v1)

1. Working PWA, installable on iOS Safari and Android Chrome
2. End-to-end demo flow: capture receipt → OCR → assign → share Venmo links → settle
3. 50+ real users across Phi Psi, dorm, and friend groups; real bills processed
4. $0 ongoing API or infrastructure costs
5. Polished public artifact: open GitHub repo with documented hours, AI tool usage, and weekly progress
6. Class presentation that lands the thesis cleanly

## Non-goals (v1)

Explicitly out of scope. Each was considered and cut to protect the 10-week timeline:

- Multi-currency
- Trip / multi-day expense tracking
- Recurring splits (rent, utilities)
- Plate-photo AI assignment ("who ate what")
- Voice input
- Settle-Up minimum-transaction algorithm (cross-bill netting)
- Bank or Plaid integration
- Auto-charging via Venmo (impossible — no public API exists)
- Native iOS / Android apps (PWA only)
- Real-world business sustainability (this is a class project)

### Data model (Drizzle, simplified)

```ts
users          // managed by Supabase Auth — referenced by id

profiles {
  id: uuid (matches auth.users.id)
  display_name: string?
  venmo_handle: string?              // host's default handle — used to autofill "pay-to" in deep links
  created_at: timestamp
}

splits {
  id: uuid
  host_user_id: uuid (fk users)
  name: string                       // "Coupa lunch" / "Tressider dinner"
  subtotal: numeric
  tax: numeric
  tip: numeric
  status: enum('open', 'closed')
  created_at: timestamp
}

split_items {
  id: uuid
  split_id: uuid (fk splits)
  name: string                       // "Burger" / "Calamari"
  unit_price: numeric
  quantity: int
  raw_ocr_line: text                 // for debugging OCR errors
}

participants {
  id: uuid
  split_id: uuid (fk splits)
  name: string
  phone: string?                     // for share targeting
  venmo_handle: string?
  total_owed: numeric                // computed, persisted on save
  paid: boolean
}

item_assignments {
  id: uuid
  item_id: uuid (fk split_items)
  participant_id: uuid (fk participants)
  share_fraction: numeric            // e.g., 0.5 if two-way split
}

receipts {
  id: uuid
  split_id: uuid (fk splits)
  image_url: text                    // Supabase Storage
  ocr_raw: text                      // for debugging
  created_at: timestamp
}
```

Tax + tip allocation defaults to **proportional** (each participant's tax = (their_subtotal / bill_subtotal) × bill_tax). Host can override per-participant if needed.

## Key user flows

### Flow 1: Create a bill (the magic moment)

1. Host taps "New bill" on home screen
2. Camera opens (or upload from photos)
3. Tesseract.js runs in-browser; spinner; items list appears (~2–4 seconds)
4. Items list shown; host taps any item to edit name/price (OCR errors are normal — UI assumes this)
5. Host adds participants — name only required, phone/Venmo optional
6. For each item: tap → checkboxes for who had it (multi-select supports shared items)
7. Tax/tip auto-allocated proportionally; host can override
8. Per-person totals shown clearly
9. Tap "Send" → for each participant with phone or Venmo:
   - Web Share Sheet opens with prefilled message + Venmo deep link
   - Host taps share target (iMessage / WhatsApp / SMS / copy)
10. Bill saved to history with status "open"

**Target time:** under 30 seconds from camera-open to share-fired for a 4-person bill.

### Flow 2: Settlement + reminders

1. Host opens app → "Splits" tab → bills with status badges
2. Open a split → see per-person paid/unpaid state (host marks manually)
3. For unpaid: tap "Remind" → Web Share Sheet opens with prefilled nudge ("Hey, here's your tab from Coupa — $14.20") + their Venmo link
4. Web Push notification fires 48 hours after creation if any unpaid balances remain → tapping notification opens the split detail
5. Status auto-closes when all participants marked paid

### Flow 3: First-time onboarding

1. User opens cover.app on phone
2. Google sign-in (or magic link fallback)
3. Prompt: "Install Cover on your home screen" with iOS- and Android-specific instructions
4. Brief 3-screen onboarding explaining how it works
5. Land on "New bill" CTA

## AI / runtime strategy

The runtime AI surface is intentionally minimal to honor the **no-API-keys** constraint:

- **Receipt OCR:** Tesseract.js in-browser. ~85% accuracy on clean receipts. Errors are user-correctable in 1–2 taps. The UI assumes errors will happen.
- **Optional smart features (Chrome desktop only):** When `window.ai` is available, use the Prompt API for:
  - Heuristic for whether a parsed line is a real item vs a tax/discount/total line
  - Drafting friendly reminder copy
  - Item category inference (food/drink/other)
- **iOS / non-Chrome users:** None of the optional features run. The app is fully functional without them.

**The "AI thesis" lives in the build process, not the runtime:**
- All code written via Cursor / Claude Code
- `docs/build-log.md` tracks hours per task, prompts used, % code generated
- README publishes running totals: hours worked, AI-vs-human contribution split, deploys to production

## Venmo deep linking

Venmo supports a public URL scheme:

```
https://venmo.com/{username}?txn=pay&amount={amount}&note={url-encoded-note}
```

On phones with Venmo installed, this opens the app with recipient and amount prefilled. The recipient still taps "Send" — there is no public API to auto-execute payment. **This is industry standard, including Splitwise.**

If a participant has no Venmo handle stored, the share sheet sends the amount + bill description and the recipient pays however they prefer.

## Auth approach

Supabase Auth, ported from Conductor:
- Google OAuth (preferred — most Stanford students have a Stanford Google account)
- Magic link (fallback)

**Only the host needs an account.** Participants receive a Venmo link through a share sheet without ever signing up — drastically lower friction. If a participant later wants their own running tab view, they can sign up; this is post-v1.

## Error handling

| Failure | Behavior |
|---|---|
| OCR fails (blurry, blocked camera) | Fallback to "Add items manually" form |
| Tesseract.js worker crash | Retry with size-reduced image; if still fails, manual entry |
| Web Share API unsupported | Copy-to-clipboard with toast |
| Web Push permission denied | Silently fail; reminders work as in-app badges only |
| Supabase down | Local-first save with sync queue (stretch) |
| No internet | Same as above |

## Risks

1. **Tesseract.js OCR quality** — if much worse than expected, the magic-moment demo falls flat.
   *Mitigation:* "tap to fix" UI from day 1; receipt photo retake flow; never block the user on perfect OCR.
2. **iOS Safari PWA quirks** — Push API support was 16.4+, file uploads can be flaky, install flow is non-obvious.
   *Mitigation:* test on real iPhones in week 2, not week 9. Build the install-instructions screen early.
3. **Temptation to add a paid AI escape valve** — if Tesseract is too weak, we'll be tempted to add Anthropic.
   *Mitigation:* hold the line. Authorize a one-time $20 budget if it becomes a blocker, but treat that as a fallback only.
4. **Time slippage during finals** — weeks 8–9 of the quarter overlap with finals at Stanford.
   *Mitigation:* core demo shippable by week 7; weeks 8–10 are polish + launch + measurement.
5. **Naming collisions** — "Cover" is a common English word; potential search confusion.
   *Mitigation:* register cover.app or similar early. Be prepared to rename if this becomes a real post-class product.
